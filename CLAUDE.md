# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Visão geral

Portfólio pessoal de Thiago Martins: SPA em React 18 criada com Create React App (`react-scripts` 5), sem backend. Todo o texto da interface, do conteúdo e dos commits é em **pt-BR**. Site publicado: https://thiagodmartins.dev.

## Comandos

```bash
npm install                 # node_modules não é versionado
npm run dev                 # dev server; porta lida de .env.development.local (PORT=3070)
npm start                   # mesmo dev server, mas com .env.production.local (PORT=3080)
npm run build               # build de produção em ./build
npm run lint                # ESLint (.js/.jsx) — roda no CI
npm run lint:styles         # Stylelint em todos os .css — roda no CI
npm test                    # Jest em modo watch (react-scripts test)
CI=true npm test -- src/App.test.js        # um arquivo, sem watch
CI=true npm test -- -t "nome do teste"     # um teste pelo nome
npm run compose:up:dev      # container dev (hot reload via volumes de src/ e public/)
npm run compose:up:prod     # container nginx com o build, porta 3080
```

Os scripts `dev`/`start`/`build` carregam `.env.*.local` via `node -r dotenv/config`. Crie esses arquivos a partir dos `.example` (estão no `.gitignore`). Os scripts `compose:*` usam o binário legado `docker-compose`.

## Arquitetura

- **O conteúdo fica todo em [src/database/data.json](src/database/data.json).** Os componentes importam o JSON direto, sem props, Context ou estado global. Alterar experiência, educação, skills, projetos, contatos ou o link do currículo é editar só esse arquivo; a maioria dos commits é `chore(data.json): ...`. Chaves principais: `profile` (incluindo `description.paragraphs`, `contacts`, `otherInformations`), `professional` (`experience`, `education`, `skills`) e `projectsSection.projects`.
- **Strings com HTML.** `profile.description.paragraphs` e os `description[]` de experiência e educação são renderizados com `dangerouslySetInnerHTML` (a regra `react/no-danger` está desativada de propósito em `.eslintrc.json`). Os links dentro dessas strings usam aspas simples e classes por empresa/instituição (`link-trybe`, `link-prodados`, `link-avoque-consultores`, `link-ifes`, `link-coursera`...). Essas classes ficam em `src/components/About/index.css` e `src/components/Resume/index.css`. No CRA todo CSS importado é global, então uma classe definida em um arquivo vale para a página inteira. Uma instituição nova precisa de uma classe nova em um desses arquivos.
- **Tela de carregamento.** Fica no `public/index.html`, fora do `#root` (o React substitui o conteúdo do `#root` ao renderizar), com estilos inline para aparecer antes do JavaScript e do CSS da aplicação. Um script inline marca `window.loadingScreenShownAt` e adiciona a classe `is-loading` no `<html>`, que trava a rolagem. O `App` chama `hideLoadingScreenWhenReady` (`src/loadingScreen.js`) depois de montar, e a tela some quando a fonte Poppins (pesos 200/400/600) e as imagens do `#root` estão decodificadas, respeitando o **mínimo de 1 segundo** de exibição e um limite de 3 segundos de espera para conexões lentas. Uma animação CSS esconde a tela após 10 segundos caso o JavaScript falhe, e um `<noscript>` a esconde quando o JavaScript está desativado. O `<link rel="preload">` da foto de perfil faz o download dela começar junto com o do JavaScript. Com a página oculta (aba em segundo plano), o navegador não decodifica imagens, então a tela só some pelo limite de 3 segundos.
- **Navegação sem rotas.** Existe só a rota `/` (`App.jsx` → `pages/Home`, que renderiza `Profile` + `MainCard`). As abas Sobre/Resumo/Projetos são definidas no array `NAVBAR_OPTIONS` do `MainCard` (`id`, `label` do botão, `title` exibido e o componente `Content`). O estado guarda só o `id` da aba selecionada, e a aba ativa recebe a classe `navbar-option-active` e `aria-pressed`. As três abas ficam **montadas ao mesmo tempo**, cada uma num `.div-main-card-panel`, e as inativas recebem o atributo `hidden`; a troca de aba só mostra e esconde, sem recriar componentes nem recarregar imagens. Só a aba inicial é montada de cara: as outras são montadas (ocultas) depois do evento `load` da página, via `requestIdleCallback`, para que as imagens não disputem a conexão com a primeira tela; uma aba clicada antes disso é montada na hora. Não use `display` no CSS do `.div-main-card-panel`, senão o `hidden` deixa de esconder o painel. Como as abas não são recriadas, a troca reinicia explicitamente o que antes vinha de graça: o fade (classe `quick-animation` no painel, de 0,8 s com `ease-in-out`, longo o bastante para parecer uma transição proposital; ela reinicia quando o `hidden` é removido e só é aplicada após a primeira troca, já que no primeiro carregamento quem revela o conteúdo é a tela de carregamento) e a rolagem interna (`scrollTop = 0` via ref; no desktop, quem rola é o card). Abaixo de 1250px quem rola é a página inteira, por isso `selectOption` também chama `window.scrollTo(0, 0)` ao trocar de aba. Como o jsdom não implementa `window.scrollTo`, o teste do `MainCard` o substitui por um `jest.fn()`. Para criar uma aba nova, basta adicionar um item ao `NAVBAR_OPTIONS`.
- **Responsividade.** Media queries em 1249 / 1023 / 767 / 579 / 480px. No desktop (a partir de 1250px) a página não rola: a `.section-home` tem `height: max(calc(100vh - 60px), 466px)` (a altura da tela menos os 30px de padding em cima e embaixo), os dois cards ocupam essa altura e quem rola é a área de conteúdo do `MainCard`. A navbar do desktop é posicionada em relação à `.section-home` (`top`/`right` = padding de 30px + 31px), então, ao mudar o padding da `.section-home`, ajuste também esses valores no `MainCard`. Para o `Profile` caber em telas baixas, ele tem dois níveis de compactação por altura (`max-height: 669px` e `max-height: 574px`, só com `min-width: 1250px`), que reduzem foto, nome e espaçamentos; o mínimo de 466px é a altura dele no nível mais compacto, e só abaixo disso a página volta a rolar. Não use `overflow` com rolagem no `.aside-profile`: dentro do flex isso deixa o card encolher além do conteúdo, e os contatos quebram linha. Abaixo de 1249px a navbar vira barra fixa no rodapé e o `Profile` vira um menu expansível. Também abaixo de 1249px quem rola é a página inteira, e não a área de conteúdo do card: por isso o `.content-render-section` usa `overflow: hidden` (sem reservar espaço para barra de rolagem) e os 30px de espaçamento à direita da `.ul-list-timeline` e da `.section-skills` são removidos. Esses 30px só existem no desktop, para afastar o conteúdo da barra de rolagem interna do card; sem essa barra, o lado direito ficaria mais espaçado que o esquerdo. O botão desse menu é sempre renderizado, e só o CSS decide quando ele aparece (abaixo de 1249px). Não leia `window.innerWidth` para isso: os breakpoints ficam apenas no CSS. O botão tem só uma seta, com `aria-label="Mais informações"`. A seta gira 180° com o seletor `[ aria-expanded = 'true' ]`, então o estado visual vem do mesmo atributo que os leitores de tela anunciam. O destaque de foco usa `:focus-visible`, que aparece só na navegação por teclado. A animação de abrir e fechar os contatos usa `grid-template-rows` de `0fr` para `1fr` na seção, com um wrapper `.div-profile-more-info-content` que tem `overflow: hidden` e recorta o conteúdo durante a transição. Não volte a usar `max-height` com valores fixos: a animação deixaria de acompanhar a altura real e o conteúdo vazaria. Os contatos aparecem em cascata via a variável CSS `--item-index`, e tudo fica sem animação com `prefers-reduced-motion`. No celular e no tablet, a linha separadora acima dos contatos é desenhada pelo pseudo-elemento `.section-profile-more-info:before` (a borda real fica transparente, mantendo o 1px do layout), com transição de opacidade própria: aparece só na segunda metade da abertura e some nos primeiros 100 ms do fechamento, para não encostar na foto enquanto a margem anima.
- **Destaque automático das skills.** O hook `src/components/Resume/useSkillsHighlight.js` destaca um card de "Minhas Skills" por vez, em loop, a cada `SKILL_HIGHLIGHT_INTERVAL` (1 s). O destaque usa a classe `skill-highlighted`, com o mesmo estilo do `:hover` do `SmallCard`. A transição de 1 s `ease-in-out` fica no próprio `.skill`, então vale igualmente para o destaque automático e para o hover do mouse; se mudar o intervalo, mude também essa transição. O destaque pausa com o mouse sobre qualquer card e volta `SKILL_HIGHLIGHT_RESUME_DELAY` (1 s) depois de o mouse sair. Ele só roda com a grade visível (via `IntersectionObserver`, já que a aba "Resumo" fica montada oculta) e sem `prefers-reduced-motion`.
- **Assets.** Caminhos locais começam com `/assets/...` e são servidos de `public/assets/`. Imagens de projetos ficam em `public/assets/projects-images/` e ícones de skills em `public/assets/skills/`; todas as imagens são servidas pelo próprio site, sem URLs externas. Imagens raster de projetos são WebP com no mínimo 750×400 (o dobro do maior card, 374×200, para telas 2×) e no máximo isso quando o original for maior; o card não usa `object-fit`, então a imagem é esticada para a caixa e não deve ser recortada. Imagens de projeto em SVG **não** são esticadas: o navegador mantém a proporção do `viewBox` e centraliza o desenho na caixa (que vai de 290×200 a 374×200). Por isso, o fundo do SVG deve ser um `style="background-color:..."` no elemento `<svg>` (cobre a caixa inteira em qualquer largura; um `<rect>` de fundo só cobre até onde se estende), e o `viewBox` deve ter o centro no centro do desenho, senão o desenho aparece deslocado no card. Ícones de skills: SVG quando houver; imagens raster com até 120px (o dobro dos 60px exibidos), no formato que ficar menor. Antes de adicionar um SVG de terceiros, confira que ele não tem `<script>`, atributos `on*`, `foreignObject` nem referências externas, já que ele passa a ser servido pelo domínio do site.
- **Foto de perfil e ícones.** A foto (`public/assets/thiago-martins.webp`) é um WebP de 320×320, o dobro dos 160px máximos que ela ocupa na tela (para telas de alta densidade). Os ícones são gerados a partir da mesma foto:
  - `public/favicon.ico` (16/32/48px), usado no `index.html` e no `manifest.json`;
  - `public/logo192.png` e `public/logo512.png`, usados no `manifest.json`;
  - `public/apple-touch-icon.png` (180px), com fundo `#121212` no lugar da transparência, porque o iOS preenche transparência com preto.
  - Ao trocar a foto, gere todos esses arquivos de novo. Ícones ficam em PNG/ICO, não em WebP, porque o iOS e alguns navegadores não aceitam WebP nesses usos.

## Convenções de código

- **ESLint** usa `@trybe/eslint-config-frontend`: espaços dentro das chaves no JSX (`{ value }`, `className={ x }`), aspas simples e indentação de 2 espaços.
- **Stylelint** (`.stylelintrc.json`) é estrito:
  - propriedades em **ordem alfabética** (`stylelint-order`);
  - media queries no formato `@media screen and ( max-width : 1249px )`;
  - linha em branco antes de cada at-rule, aspas simples, cores hex em minúsculo/curtas;
  - proibido `!important`, prefixos de vendor e seletores qualificados por tipo.
- O CSS existente usa `0.001px` onde o valor seria zero. Siga o padrão do arquivo que estiver editando.
- Cada componente tem `index.jsx` + `index.css` na própria pasta.
- A fonte Poppins é carregada **uma única vez**, por um `<link>` no `public/index.html`, com os pesos `200;400;600`. Não use `@import` de fontes nos CSS. Se passar a usar um peso novo em `font-weight`, adicione-o nessa URL.
- As tags `<b>` do `data.json` usam o padrão do navegador (`bolder`), que é relativo ao texto em volta: nos parágrafos com peso `200`, o negrito fica com peso `400`. Isso é intencional, porque o peso `700` foi testado e achado agressivo demais. Não force `font-weight` no `<b>`.
- **Commits** seguem [Conventional Commits](https://www.conventionalcommits.org) + gitmoji, em pt-BR. O formato é `tipo(escopo): :gitmoji: Descrição`, com corpo opcional explicando o porquê.
  - O tipo segue a natureza da mudança (`feat`, `fix`, `refactor`, `test`, `ci`, `docs`, `chore`...).
  - O gitmoji corresponde ao tipo.
  - O escopo é o nome do arquivo alterado (`data.json`, `index.css`, `index.yml`, `README.md`...).
  - Exemplos: `chore(data.json): ...`, `test(App.test.js): :white_check_mark: ...`, `ci(index.yml): :construction_worker: ...`.
  - Siga o padrão, não os commits antigos: alguns não têm escopo ou gitmoji.

## CI/CD e branches

- O trabalho é feito em `dev-thiago-martins` e entra por PR na `main`.
- A `main` é protegida: o merge exige que os checks `Run linters ESLint and Stylelint`, `Run tests` e `Build Application` passem. **Não renomeie esses jobs** sem atualizar também a regra de proteção no GitHub, senão os PRs ficam esperando um check que nunca chega.
- `.github/workflows/index.yml` só valida e não faz deploy. Ele roda em PRs para a `main` e em `push` na `main`: `linters` (`lint` + `lint:styles`) e `tests` (`npm test -- --watchAll=false`) rodam em paralelo, e `build` só roda se os dois passarem.
- **O deploy é feito pela Vercel**, pela integração com o Git (preview em cada PR e produção no merge na `main`). Não há configuração da Vercel no repositório.
- **Vercel Web Analytics** (visitantes e visualizações de página, sem cookies) é carregado por um script inline no `public/index.html`, que injeta `/_vercel/insights/script.js`, servido pela própria Vercel. O script só é injetado no build de produção (`'%NODE_ENV%' === 'production'`), então no `npm run dev` nada é carregado; no container de produção (nginx), a requisição do script dá 404, sem efeito no site. O pacote `@vercel/analytics` não é usado: o `npm install` dele falha com `ERESOLVE`, porque um peer opcional dele (`@sveltejs/kit`) pede TypeScript 5, e o `react-scripts` 5 fixa o TypeScript 4. O componente `<Analytics />` do pacote injeta exatamente esse mesmo script em produção.
- O deploy antigo no GitHub Pages (branch `gh-pages`) foi desativado. A história está registrada no README; não recrie esse job.
- O GitHub Actions define `CI=true`. Com isso, o `react-scripts build` trata warnings do ESLint como erro, e os testes rodam uma única vez.
- O CI usa Node 24 com `npm ci`, então o `package-lock.json` precisa estar sincronizado com o `package.json`. Lint e build foram validados no Node 22 e 24; no 24 aparece só um aviso de depreciação (`fs.F_OK`), que não afeta o build.
- Rodar `npm run lint:styles` depois de um build local também analisa o CSS minificado em `build/` e gera milhares de erros. Apague `build/` antes.
- **Docker** tem um Dockerfile por ambiente, ambos com Node 24:
  - `Dockerfile.dev`, usado pelo `docker-compose.dev.yaml`: roda `npm run dev` na porta 3070, com `src/` e `public/` montados como volume para o hot reload;
  - `Dockerfile.prod`, usado pelo `docker-compose.prod.yaml`: multi-stage, compila no estágio `node` e a imagem final só tem o `nginx:alpine` com o conteúdo de `build/` (~46 MB).
  - Os dois copiam `package.json` e `package-lock.json` antes do código e usam `npm ci`, para aproveitar o cache de camadas do Docker.
  - O `docker-compose.prod.yaml` exige o arquivo `.env.production.local` (crie a partir do `.example`), mesmo o nginx não usando a variável `PORT`.

## Armadilhas conhecidas

- Testes: `src/App.test.js` é um smoke test que renderiza o `App` dentro de um `MemoryRouter`, `src/components/MainCard/index.test.js` testa a troca de abas e o pré-carregamento das abas ocultas (com `hidden`, elas não aparecem nas buscas por papel do Testing Library sem `hidden: true`) e `src/components/Profile/index.test.js` testa o botão "Mais informações" `src/components/Resume/index.test.js` testa o destaque automático das skills (com timers simulados e um `IntersectionObserver` falso, já que o jsdom não o implementa) e `src/loadingScreen.test.js` testa o tempo mínimo da tela de carregamento (com timers reais, por isso leva cerca de 1 segundo). Eles dependem do `profile.myName` do `data.json` e dos `label`/`title` do `NAVBAR_OPTIONS`; se você alterar algum deles, atualize os testes. Arquivos `*.test.js` estão no `.eslintignore`.
